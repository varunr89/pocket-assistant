# QA Test Plan — Schedule-Gated Capture (M1 increment 3a)

**Status:** Proposed; Varun approval required before execution · **Target:** approved `b76a0af`, debug APK, `com.varun.pocketassistant` · **Device:** real Pixel via ADB

## Gate and method

Verify the customer contract: the weekly schedule, or its explicit override, is the sole authority for capture. With the default local-time schedule (Mon–Fri 08:00–17:00), speech inside the window must produce a persisted segment and raw-audio file; identical speech outside it must produce **zero new segment rows and zero new/grown audio-file bytes**. Existing session rows are not failures. Use one consented, repeatable 15-second speech clip at fixed volume/distance, followed by enough silence for segment finalization; the inside-window run is the VAD positive control.

After approval, the executor will: verify `adb devices -l`; record device/build/package identity; install the supplied APK with `adb install -r app/build/outputs/apk/debug/app-debug.apk` (never uninstall or `pm clear`); grant/confirm mic and notification permissions; and record `adb shell date`, `adb shell getprop persist.sys.timezone`, automatic-time settings, and battery state. State comes from the app/notification plus `adb shell dumpsys activity services com.varun.pocketassistant`; transitions come from timestamped `adb logcat -v threadtime` filtered to `AudioCaptureEngine`/`RecordingService`.

For every named checkpoint `<ID>-<phase>`, save under `docs/qa/results/2026-09-08-schedule-gated-capture/evidence/`:

- `<checkpoint>-clock.txt`, `<checkpoint>-screen.png`, `<checkpoint>-service.txt`, and `<checkpoint>-logcat.txt` (including “mic on/off”, “Opened segment”, and “Saved segment” lines where applicable).
- `<checkpoint>-segments.tsv`: `id, sessionId, filePath, startedAtMs, endedAtMs, byteSize` plus `COUNT(*)`/`SUM(byteSize)` for the test interval; `<checkpoint>-settings.tsv`: `SELECT key,value FROM settings WHERE key='capture_schedule'`.
- `<checkpoint>-audio.tsv`: path, byte size, and mtime for every file under the app sandbox’s `files/sessions/`. Use `adb shell run-as com.varun.pocketassistant ... stat ...`; snapshot `databases/pocket_assistant.db` plus `-wal`/`-shm` with `adb exec-out run-as ... cat ...` and query with host `sqlite3`. At an endpoint, collect UI/log/service evidence first, then force-stop only if needed for a consistent DB snapshot, and relaunch before the next scenario.

**Cycle verdict:** PASS only if S1–S6 **and L1** pass with both independent persistence oracles (Room and on-disk bytes); any UI-only success, missing evidence, unexpected outside-window row/file growth, crash, or silent state is FAIL/BLOCKED. L1's failure is a real failure — it must be routed back to the coder (boot-receiver fix) before this increment is fully verified.

## Risks, blockers, and approvals required

- Clock travel is required for exact 08:00/17:00 and weekend/Monday coverage. Stock Pixels may reject `adb shell date -s ...`; manual Date & time UI (automatic time temporarily disabled) or a rooted/test device is required. Clock changes can corrupt chronology, alarms, tokens, and existing app records, so run this only in an approved isolated/disposable app-data context and restore the original automatic-time/timezone settings afterward.
- Blockers: Pixel unavailable/unauthorized, debug APK signature cannot update the installed app, `run-as` unavailable, active calls/other mic clients, insufficient battery/storage, unreliable test-audio trigger, or real data that may not be copied/altered. No deletion, reset, or raw-audio export is implied. **A real reboot IS part of this test (L1)** and is explicitly approved under decision (6).
- **Varun decisions before execution:** (1) authorize debug-APK install, mic use, and synthetic test recordings on this phone; (2) authorize clock/date changes and state whether QA can set them via root/manual UI, otherwise accept a multi-day real-time run; (3) choose data isolation—disposable Android user/app state vs preserving primary data (true fresh-default validation requires isolation/reset); (4) authorize pulling the Room DB/file metadata and, if needed, only the newly created test audio as evidence; (5) approve a controlled 60–90 minute device window (plus reboot time) with the phone unavailable for normal use; and (6) **approve a real reboot during the test** — the device will power-cycle and come back to the lock screen (PIN may be required); you'll need to unlock it or accept QA unlocking/reenabling remote access after boot.
